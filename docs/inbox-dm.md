# Inbox and direct messages

Every temporary or persistent Ed25519 identity owns `inbox1.<64 lowercase hex signing public key>`. No private key appears in the address. The transport maps it to `/soft-room/1/<signing public key>/json`, retaining the existing Waku Store manager's 64-hex room routing. An ordinary invitation does not grant inbox decryption access.

A sender converts the recipient's validated Ed25519 public key to X25519, generates a fresh ephemeral X25519 secret, and derives a 32-byte key with HKDF-SHA256. HKDF info and AEAD additional data bind the protocol version, recipient public key and ephemeral public key. XChaCha20-Poly1305 encrypts a JSON envelope containing the exact signed message body and its Ed25519 signature. The wire packet is version byte 1, ephemeral public key (32 bytes), random nonce (24 bytes), then ciphertext and tag. Signature verification and recipient/time/type validation precede sender-based DM grouping. The sender identity is inside the ciphertext. A reply repeats this process against the original sender's inbox, without a handshake.

This is asynchronous public-key encryption, not a ratcheting protocol: possession of the recipient's long-term private key permits decryption of recorded messages. Inbox topics are public and linkable. Transport acceptance does not prove receipt or reading. Existing seven-day, best-effort Waku history and transport availability rules still apply. Inbox subscriptions run while the app is open; there is no OS push/background service in this change. DM supports text, encrypted attachments, presence, and WebRTC signaling. Ordinary rooms and DMs use the same transport selection, attachment storage/viewer, channel UI, media lifecycle, and TURN provider.

The inbox connection has a separate lifetime from the selected room, reconnects after losing connectivity, and reads Store history on connection. Authenticated unknown senders receive an unsaved conversation with unread counts. Saved contacts have their own sidebar rows. Message histories remain in memory; incoming history is recovered from Store, while outgoing DM history is currently session-only.

Saved contacts in the temporary session are encrypted with XChaCha20-Poly1305 using a domain-separated key derived from the existing identity secret. This does not protect against scripts already able to read that identity store. Persistent contacts additionally use the existing non-extractable AES-GCM master key in local IndexedDB and AT Protocol archive records under `uk.wakukusmartrecipe.soft.contact`. Random record keys conceal contact public keys in archive paths. Master-key recovery restores contacts alongside the identity and rooms. No signing key, contact name or contact public key is stored in plaintext in those archive records.

Validation: `npm run build`, `npm test`, and `node tests/browser-dm.mjs` against the HTTPS static preview. The latter uses two real Waku browser clients, including unknown-sender grouping, replies, room switching, local contact encryption, refresh, and mobile/desktop navigation layout. Android uses the existing `android-test.yml` workflow; iOS uses the shared Capacitor web implementation and is not built for this change.

Contact deletion removes the saved label and sidebar entry. The archive keeps an encrypted deletion marker (without the saved name) so stale device snapshots cannot restore the contact. Deletion sync retries from local state after reconnecting; explicit saving can restore the contact. Deletion is not blocking: a later authenticated message creates an unsaved conversation.

## DM attachments and two-person channels

The two signing identities convert their long-term keys to X25519 and derive a shared 32-byte secret with HKDF-SHA256. The info string `soft-room/dm-room/v1:` plus the sorted pair of signing public keys separates this secret from inbox encryption. A fixed `DM` room context gives both sides the same private attachment encryption key and mesh room commitment. It is never advertised as a room invitation or stored as an ordinary saved room. Attachment bytes, optional compressed previews, encryption, storage routing, download and rendering reuse the ordinary room pipeline. The authenticated file reference travels to the recipient's Inbox.

Presence and offer/answer packets use the signed, recipient-encrypted Inbox envelope. They expire after 30 seconds, are excluded from historical DM replay and chat/unread lists, and only reach the selected peer's mesh. Channel announcements must bind to the pair's context and be signed by one of its two identities. The existing voice, video and push-to-talk channel implementation handles the actual WebRTC data and media streams. Leaving or switching the DM tears down channels and capture; the Inbox subscription continues independently.

Both room types call the same `connect()` and `activeBootstrap()` functions: normal mode uses the public fleet, hidden mode uses the configured private peer and the existing Store fallback. Both call the same ICE provider for managed TURN proof/credentials, expiry/retry behavior and relay-only connections; custom TURN settings stay local to the channel and can be disabled to return to managed TURN.

The composer computes readiness once per update. It must never briefly disable a connected DM textarea while calculating ordinary-room readiness: that dismisses Android's keyboard. `tests/browser-dm-capabilities.mjs` checks sustained mobile input focus, real encrypted attachment transfer, voice/video RTP, push-to-talk, TURN configuration and node selection; run it again with `DM_PRIVATE=1` to exercise hidden mode. These browser checks do not substitute for a physical Android keyboard/camera check.
